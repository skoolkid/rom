The ↑ operator and negative bases
Expressions such as X↑Y give an 'A Invalid argument' error when X is negative, even when Y is an integer. For example:
PRINT (-1)↑2
This is because the to_power routine computes the value as EXP (Y*LN X), and LN X is undefined for negative values of X.
Comparing numbers can overflow (or underflow)
Numeric comparisons work by subtracting one number from the other (see the subtract call at 13652). This means that:
PRINT 1e38>-1e38
gives a '6 Number too big' error instead of the expected '1'. Any comparison whose difference exceeds the largest number that can be represented in floating-point form (about 1.7e38) fails the same way.
For the same reason, slightly different very small numbers are regarded as equal when compared (because their difference rounds down to zero). For example:
PRINT 5e-39,6e-39
prints two different values, but:
PRINT 5e-39=6e-39
prints '1' (as if the values were equal).
Negative coordinates can lose their sign
Consider the following program:
10 PLOT -10,-20
20 PRINT POINT (-10,-20)
The negative coordinates apparently make no sense, but the result is a pixel plotted at (10,20), which the POINT command correctly identifies.
Likewise:
10 PRINT AT 1,2; INK 3;"a"
20 PRINT ATTR (-1,-2)
30 PRINT SCREEN$ (-1,-2)
prints '59' and 'a' (as if the minus signs were not present).
Also:
CIRCLE -100,50,0.9
results in a pixel plotted at (100,50) - because the radius is less than 1 and so it just PLOTs the point. But:
CIRCLE -100,50,1
gives a more sensible 'B Integer out of range' error.
SCREEN$ and ATTR don't check their arguments
We've already seen that ATTR and SCREEN$ are blind to negative coordinates, but they also don't care about coordinates that are out of range. For example:
10 POKE 23296,255
20 PRINT ATTR (24,0)
prints '255', because the attribute file address for (24,0) is computed as 23296, the first byte of the printer buffer (where the '25th line' of the attribute file would naturally be, if it existed).
Similarly:
10 PRINT AT 1,0; INK 3;"a"
20 PRINT ATTR (0,32)
30 PRINT SCREEN$ (0,32)
prints '59' and 'a', because (0,32) effectively resolves to (1,0).
